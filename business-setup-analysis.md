# Анализ Business Setup Module

## TL;DR

`BusinessSetupModule` — это высокоуровневый, сложный модуль-оркестратор, который управляет процессом "настройки бизнеса" (Business Setup). Он построен на современных принципах: модульная архитектура с "провайдерами" (например, Avito), продвинутая интеграция с AI с использованием Schema-Guided Reasoning (SGR), и паттерны "супервизора" и "агентов" для управления сложной логикой. Модуль предоставляет API через GraphQL (включая real-time подписки) и REST для взаимодействия с этой системой.

---

### Детальный анализ `business-setup.module.ts`

Этот модуль является центральным хабом для сложного бизнес-процесса. Давайте разберем его по частям.

#### 1. Основное назначение

Судя по названию и компонентам, `BusinessSetupModule` отвечает за пошаговую настройку или интеграцию какого-либо бизнес-процесса. Наличие `AvitoBusinessSetupProvider` и комментариев про `EbayBusinessSetupProvider` говорит о том, что система спроектирована для работы с различными внешними платформами. Процесс, вероятно, интерактивный и асинхронный, с использованием чат-ботов (`Agent` services), AI и real-time обновлений (`Subscriptions`).

#### 2. Архитектура и ключевые паттерны

Модуль реализует несколько продвинутых архитектурных паттернов:

*   **Модульная архитектура с провайдерами**: `ProviderRegistry` и конкретные реализации (`AvitoBusinessSetupProvider`) позволяют легко добавлять поддержку новых платформ (Avito, eBay и т.д.), не изменяя основную логику. Каждый провайдер инкапсулирует специфику работы с конкретной платформой.
*   **Супервизор и Агенты (Supervisor & Agents)**: Названия сервисов, такие как `SupervisorSGRService`, `BusinessSetupAgentService`, `EnhancedSupervisorToolDispatcher`, указывают на использование агент-ориентированной архитектуры.
    *   **Агент (`Agent`)**: Выполняет конкретные задачи. Например, `BusinessSetupWelcomeAgentService` может отвечать за "приветствие" и начальные шаги.
    *   **Диспетчер (`Tool Dispatcher`)**: Решает, какой инструмент или сервис (`tool`) использовать для выполнения задачи.
    *   **Супервизор (`Supervisor`)**: Управляет всем процессом, координирует работу агентов и диспетчеров, обрабатывает ошибки и следит за общим состоянием.
*   **Schema-Guided Reasoning (SGR)**: Это ключевая особенность, указывающая на глубокую интеграцию с AI. SGR — это техника, которая заставляет AI-модели (LLM) генерировать ответы в строгом соответствии с заданной схемой (например, JSON schema). Это делает AI более надежным, предсказуемым и управляемым, что критически важно для бизнес-процессов.

#### 3. Компоненты модуля (Providers)

Сервисы, зарегистрированные в `providers`, можно сгруппировать по функциональности:

*   **Ядро "Business Setup" (существующие сервисы)**:
    *   `BusinessSetupService`: Основной сервис, управляющий общей логикой.
    *   `BusinessSetupWelcomeAgentService`, `BusinessSetupAgentService`: Агенты, реализующие конкретные этапы или диалоги с пользователем.
    *   `BusinessSetupTransitionService`: Управляет переходами между состояниями/шагами процесса.
    *   `EventEmitterBridgeService`: Служит для обмена событиями внутри модуля, обеспечивая слабую связанность компонентов.

*   **Фундаментальные сервисы ("Critical Architecture Fixes")**:
    *   `BusinessSetupStatusCacheService`: Кэширует состояние процесса, чтобы снизить нагрузку на БД.
    *   `AdaptiveSupervisorConfigService`: Позволяет гибко настраивать поведение супервизора.
    *   `SupervisorErrorRecoveryService`: Отвечает за отказоустойчивость, вероятно, реализуя паттерны вроде "Circuit Breaker" для предотвращения каскадных сбоев.
    *   `StreamingProgressService`: Обеспечивает отправку обновлений о прогрессе в реальном времени на фронтенд.
    *   `SupervisorAnalyticsService`: Собирает метрики и аналитику по работе процесса.

*   **Система Провайдеров**:
    *   `ProviderRegistry`: Реестр, который хранит все доступные провайдеры.
    *   `AvitoBusinessSetupProvider`: Конкретная реализация логики для платформы Avito.

*   **SGR и AI-логика**:
    *   `SupervisorSGRService`: "Супервизор", работающий по принципу SGR.
    *   `SupervisorToolDispatcherService`: Диспетчер, который направляет задачи от SGR-супервизора к нужным инструментам.
    *   `AvitoWelcomeSGRService`, `AvitoWelcomeToolDispatcherService`: SGR-логика и диспетчер, специфичные для интеграции с Avito.
    *   `HttpTool`: Конкретный "инструмент", который агенты могут использовать для выполнения HTTP-запросов (например, для валидации API-ключей Avito).

#### 4. API и точки входа (`Controllers` и `Resolvers`)

Модуль предоставляет два типа API:

*   **GraphQL API**:
    *   `BusinessSetupResolver`: Для стандартных запросов (queries) и изменений (mutations).
    *   `BusinessSetupChatResolver`: Специализированный resolver для логики чата.
    *   `BusinessSetupSubscriptionsResolver`: Для real-time обновлений через GraphQL Subscriptions, что идеально подходит для отслеживания прогресса долгого процесса.
*   **REST API**:
    *   `SupervisorController`: Предоставляет традиционные REST-эндпоинты для управления "супервизором".

#### 5. Выводы

`BusinessSetupModule` — это не просто CRUD-модуль. Это сложная система, спроектированная для решения следующих задач:
1.  **Оркестрация**: Управление сложным, многошаговым, асинхронным бизнес-процессом.
2.  **Расширяемость**: Легкое добавление новых интеграций (провайдеров) без изменения ядра системы.
3.  **Интерактивность**: Взаимодействие с пользователем через чат-интерфейс с real-time обратной связью.
4.  **Надежность**: Использование кэширования, отказоустойчивых механизмов и предсказуемого AI (SGR).
5.  **Интеллект**: Глубокое использование AI-агентов и супервизоров для автоматизации и принятия решений.

Этот модуль является примером современной, хорошо спроектированной back-end системы для управления сложными, AI-управляемыми рабочими процессами.

### Детальный разбор классов и их взаимодействий

#### Часть 1: Ядро Модуля

Эта группа классов отвечает за управление состоянием всего процесса "Business Setup", определение текущего шага и создание/поиск нужных AI-агентов.

##### 1. `BusinessSetupService`
-   **Файл**: `business-setup.service.ts`
-   **Роль**: **"Менеджер Состояний" (State Manager)**. Это главный сервис, который знает, на каком этапе находится пользователь в процессе настройки.
-   **Ключевые зависимости**:
    -   `UserVarsService`: Сервис для хранения и извлечения пар "ключ-значение", связанных с конкретным пользователем и рабочим пространством. Именно здесь хранится флаг текущего шага (`BUSINESS_SETUP_WELCOME_PENDING: true`).
    -   `OnboardingService`: Проверяет, завершил ли пользователь базовый онбординг, прежде чем начать "Business Setup".
    -   `EventEmitter2`: Используется для **децентрализованной обработки событий**. Сервис не вызывает `SupervisorSGRService` напрямую, а генерирует событие (`BUSINESS_SETUP_ROUTE_MESSAGE`), на которое подписываются другие сервисы. Это отличный пример слабосвязанной архитектуры.
-   **Основные методы**:
    -   `getBusinessSetupStatus()`: Определяет текущий активный шаг, последовательно проверяя флаги в `UserVarsService`.
    -   `setBusinessSetupStatus()`: Устанавливает новый шаг, сбрасывая все старые флаги и устанавливая один новый.
    -   `handleRouteMessage()`: Обработчик события, который получает сообщение от пользователя и инициирует его обработку "Супервизором", генерируя новое событие `SUPERVISOR_PROCESS_MESSAGE`.
-   **Взаимодействие**: `BusinessSetupService` является центральным узлом для управления состоянием. Другие сервисы (например, `BusinessSetupTransitionService`) вызывают его для изменения шага, а он, в свою очередь, запускает AI-логику через систему событий.

##### 2. `BusinessSetupAgentService`
-   **Файл**: `services/business-setup-agent.service.ts`
-   **Роль**: **"Фабрика Агентов" (Agent Factory)**. Этот сервис отвечает за создание и предоставление нужного AI-агента для каждого конкретного шага процесса.
-   **Ключевые зависимости**:
    -   `Repository<AgentEntity>`: Для прямого доступа к таблице агентов в БД.
    -   `AgentService`: Более высокоуровневый сервис для управления агентами.
-   **Основные методы**:
    -   `getAgentForStep()`: Главный метод. Принимает на вход текущий шаг (`BusinessSetupStatus`) и возвращает соответствующий `AgentEntity`.
    -   **Логика**:
        1.  Он проверяет, существует ли уже агент для этого шага в данном `workspace`.
        2.  Если нет, он вызывает `createAgentForStep` для создания нового.
        3.  **Особый случай**: Для шага `WELCOME` он всегда использует специального SGR-агента (`sgr-avito-agent`) с захардкоженным ID, который обладает расширенными возможностями.
    -   `createAgentForStep()`: Содержит "рецепты" для создания агентов. Для каждого шага здесь определены: имя, описание, системный промпт и используемая модель (`google/gemini-2.5-flash` или `auto`).
    -   `getSupervisorAgent()`: Аналогично, получает или создает главного "Супервизор-Агента".
-   **Взаимодействие**: Этот сервис вызывается, когда системе нужно передать управление AI. Например, `SupervisorSGRService` может запросить у него агента для `BUSINESS_ANALYSIS`, чтобы делегировать ему диалог с пользователем.

##### 3. `BusinessSetupTransitionService`
-   **Файл**: `chat-continuation/business-setup-transition.service.ts`
-   **Роль**: **"Диспетчер Переходов" (Transition Controller)**. Управляет логикой перехода от одного шага к другому.
-   **Ключевые зависимости**:
    -   `BusinessSetupService`: Использует его для фактического изменения состояния (`setBusinessSetupStatus`).
    -   `EventEmitter2`: Генерирует событие `business-setup.step-transition` при успешном переходе.
-   **Основные методы**:
    -   `transitionToNextStep()`: Основной метод, который получает текущий и следующий шаг, проверяет валидность перехода и вызывает `BusinessSetupService` для обновления состояния.
    -   `isValidTransition()`: Содержит "карту" разрешенных переходов. Например, с `WELCOME` можно перейти только на `BUSINESS_ANALYSIS`. Это предотвращает нарушение последовательности процесса.
    -   `getNextStep()`: Простая функция, которая по текущему шагу возвращает следующий.
    -   `getBusinessSetupProgress()`: Рассчитывает и возвращает общий прогресс в процентах.
-   **Взаимодействие**: Этот сервис используется, когда один из агентов или "Супервизор" решает, что текущий шаг завершен. Он вызывает `transitionToNextStep`, что, в свою очередь, обновляет состояние через `BusinessSetupService`, и система готова к работе со следующим агентом.

#### Часть 2: Архитектура "Супервизор-Агент" (AI-ядро)

Эта система реализует паттерн "Chain of Thought" (Цепочка Мышления), где AI (LLM) не просто отвечает на вопрос, а выполняет последовательность шагов, используя predefined "инструменты" (tools) для достижения цели. Все это происходит в рамках Schema-Guided Reasoning (SGR), что заставляет AI выдавать результат в строго типизированном JSON-формате.

##### 4. `SupervisorSGRService`
-   **Файл**: `sgr/services/supervisor-sgr.service.ts`
-   **Роль**: **"AI-Супервизор" / "Мозг"**. Этот сервис является ядром AI-логики. Он берет сообщение пользователя и решает, что с ним делать, координируя всю дальнейшую работу.
-   **Ключевые зависимости**:
    -   `AiModelRegistryService`: Для получения доступа к AI-модели (LLM), в данном случае Gemini (`google/gemini-2.5-flash`).
    -   `SupervisorToolDispatcherService`: **Ключевая зависимость**. Супервизор сам не выполняет действия, он только решает, *какой инструмент* использовать. Выполнение он делегирует Диспетчеру.
    -   `EventEmitter2`: Активно используется для публикации событий о ходе своей "мыслительной" деятельности (`SUPERVISOR_THINKING_STEP`, `SUPERVISOR_ROUTING_COMPLETED`), что позволяет, например, показывать на фронтенде "AI is thinking...".
-   **Логика работы**:
    1.  **Запуск по событию**: `handleProcessMessageEvent` запускается, когда `BusinessSetupService` генерирует событие `SUPERVISOR_PROCESS_MESSAGE`.
    2.  **Инициализация "Мышления"**: Метод `processMessageWithStreaming` запускает "цикл мышления" (`executeSGRWorkflowWithStreaming`).
    3.  **Системный Промпт**: В LLM передается огромный системный промпт (`SUPERVISOR_SYSTEM_PROMPTS`), который объясняет AI его роль, цели, доступные инструменты и **"КРИТИЧЕСКИЕ ПРАВИЛА МАРШРУТИЗАЦИИ"**. Например, правило "Для статуса WELCOME: ВСЕГДА направляй к sgr-avito-agent".
    4.  **Цикл Мышления (ReAct Pattern)**:
        a.  **Reason**: На каждом шаге (`executeReasoningStepWithStreaming`) сервис обращается к LLM с текущим диалогом и задачей. Он просит AI вернуть JSON-объект, соответствующий схеме `SupervisorStepSchema`. Этот JSON содержит "мысли" AI (`current_state`, `plan_remaining_steps`) и, самое главное, **выбранный инструмент и его параметры** (`function`).
        b.  **Act**: Выбранный инструмент (`stepResult.function`) передается в `toolDispatcher.dispatch()` на исполнение.
        c.  **Observe**: Результат выполнения инструмента добавляется в историю диалога, и цикл повторяется, пока AI не выберет "завершающий" инструмент (`complete_routing`).
-   **Взаимодействие**: Это центральный оркестратор. Он получает задачу, думает, делегирует выполнение Диспетчеру, анализирует результат и снова думает, пока задача не будет решена.

##### 5. `SupervisorToolDispatcherService`
-   **Файл**: `sgr/services/supervisor-tool-dispatcher.service.ts`
-   **Роль**: **"Диспетчер Инструментов" / "Руки"**. Этот сервис является исполнительным механизмом для "Супервизора". Он получает от него команду (JSON-объект с названием инструмента и параметрами) и выполняет соответствующий код.
-   **Ключевые зависимости**:
    -   `BusinessSetupAgentService`: Для получения агента, к которому нужно перенаправить пользователя.
    -   `AvitoWelcomeSGRService`: Для передачи управления специализированному SGR-процессу на этапе `WELCOME`.
    -   `UserVarsService`: Для проверки и изменения статуса `Business Setup`.
-   **Основные "Инструменты" (методы)**:
    -   `dispatch()`: Главный метод-маршрутизатор. Использует `switch` по `tool.tool` для вызова нужного внутреннего метода.
    -   `executeCheckBusinessSetupStatus()`: Проверяет текущий статус пользователя.
    -   `executeRouteToSpecializedAgent()`: **Ключевой инструмент**. Находит нужного агента через `BusinessSetupAgentService` и передает ему управление. Если статус `WELCOME`, вызывает `avitoWelcomeSGRService`.
    -   `executeStatusChange()`: Вызывает `updateBusinessSetupStatus` для перехода на следующий шаг.
    -   `executeProcessDirectly()`: Инструмент для простых ответов, когда не нужно привлекать других агентов.
    -   `executeCompleteRouting()`: Инструмент-терминатор, который завершает "цикл мышления".
-   **Взаимодействие**: Является "мостом" между декларативным миром AI (решениями Супервизора) и императивным миром кода (вызовами конкретных сервисов). Он получает команду от "мозга" и выполняет её, используя "руки" — другие сервисы.

#### Часть 3: Расширяемость, отказоустойчивость и API

Эта группа классов обеспечивает модульность, надежность и предоставляет внешние интерфейсы для взаимодействия с системой.

##### 6. `ProviderRegistry` и `BusinessSetupProvider` (Абстракция)
-   **Файл**: `services/provider-registry.service.ts`
-   **Роль**: **"Реестр Провайдеров"**. Этот сервис реализует паттерн "Реестр" и "Абстрактная Фабрика".
-   **Ключевые компоненты**:
    -   `BusinessSetupProvider`: Абстрактный класс, который определяет "контракт" для всех провайдеров. Любой класс, который хочет быть провайдером (например, для eBay, Stripe и т.д.), должен наследовать этот класс и реализовать его методы (`validateCredentials`, `setupBusiness` и др.).
    -   `ProviderRegistry`: Сервис, который содержит `Map` всех зарегистрированных провайдеров. Он позволяет:
        -   Регистрировать новых провайдеров (`registerProvider`).
        -   Находить нужного провайдера по ID (`getProvider`).
        -   Находить всех провайдеров, которые поддерживают определенный шаг (`getProvidersForStatus`).
-   **Взаимодействие**: Это ядро расширяемой архитектуры. Когда "Супервизору" нужно выполнить действие, специфичное для интеграции (например, проверить ключи API Avito), он не обращается к `AvitoBusinessSetupProvider` напрямую. Вместо этого он запрашивает у `ProviderRegistry` провайдера, который соответствует текущему контексту, и работает с ним через абстрактный интерфейс `BusinessSetupProvider`.

##### 7. `AvitoBusinessSetupProvider` (Конкретная реализация)
-   **Файл**: `providers/avito-provider.service.ts`
-   **Роль**: **"Провайдер для Avito"**. Это конкретная реализация `BusinessSetupProvider`, которая инкапсулирует всю логику работы с Avito.
-   **Ключевые зависимости**:
    -   `HttpService`: Для выполнения HTTP-запросов к API Avito.
    -   `UserVarsService`: Для безопасного сохранения учетных данных (`clientId`, `clientSecret`) пользователя.
-   **Логика**: Реализует все абстрактные методы "контракта":
    -   `validateCredentials`: Отправляет запрос к `https://api.avito.ru/token`, чтобы проверить, валидны ли `clientId` и `clientSecret`.
    -   `setupBusiness`: Сохраняет валидные учетные данные.
    -   `getSetupSteps`: Возвращает шаги, необходимые для настройки именно этой интеграции.
-   **Взаимодействие**: Этот класс регистрируется в `ProviderRegistry` при старте приложения и используется, когда `BusinessSetupStatus` находится в состоянии `WELCOME`.

##### 8. Вспомогательные сервисы
-   **`BusinessSetupStatusCacheService`**:
    -   **Роль**: **"Кэш состояний"**. Оборачивает `CacheStorageService` и предоставляет простой интерфейс для кэширования текущего `BusinessSetupStatus` пользователя с TTL (временем жизни) в 5 минут. Это значительно снижает количество запросов к БД для определения статуса.
-   **`SupervisorErrorRecoveryService`**:
    -   **Роль**: **"Сервис отказоустойчивости"**. Предоставляет обертку `executeWithRetry` для выполнения критически важных операций.
    -   **Логика**: Реализует сложную логику повторных попыток с **экспоненциальной задержкой** (exponential backoff) и **джиттером** (jitter) для предотвращения "стада". Он также классифицирует ошибки (`classifyError`) на `network`, `authentication`, `timeout` и решает, является ли ошибка **восстановимой** (`recoverable`) и стоит ли вообще повторять попытку.

##### 9. API (Точки входа)
-   **`BusinessSetupResolver`**:
    -   **Роль**: **GraphQL API**. Предоставляет две основные GraphQL-операции:
        -   `getBusinessSetupStatus` (Query): Получить текущий статус.
        -   `setBusinessSetupStatus` (Mutation): Принудительно установить новый статус.
-   **`SupervisorController`**:
    -   **Роль**: **REST API**. Предоставляет более сложный и функциональный API для фронтенда:
        -   `POST /supervisor/ui-guidance`: **Централизованный роутинг**. Фронтенд запрашивает у этого эндпоинта "подсказку", что отобразить пользователю (текст кнопки, иконку, тултип). Это заменяет множество проверок статуса на фронтенде.
        -   `POST /supervisor/execute-action`: Выполняет действие, инициированное пользователем.
        -   `GET /supervisor/progress/:operationId` (SSE): **Real-time обновления**. Использует Server-Sent Events для стриминга прогресса выполнения долгой операции на фронтенд.

### План по реализации расширенного стриминга и визуализации (SGR Streaming & Visualization Plan)

Этот план основан на анализе предоставленного Python-скрипта (`SGR Research Agent`) и адаптирует его ключевые концепции для вашей архитектуры на NestJS (бэкенд) и React (фронтенд).

#### 1. Концепция (Concept)

**Цель**: Воспроизвести в веб-интерфейсе детализированную real-time визуализацию "мыслительного процесса" SGR-агента, аналогично тому, как это делает Python-скрипт в терминале с помощью библиотеки `rich`.

**Подход**:
1.  **Бэкенд**: Модифицировать `SupervisorSGRService` так, чтобы он не просто ждал полного JSON-ответа от LLM, а отправлял на фронтенд "сырой" поток токенов по мере их поступления.
2.  **Фронтенд**: Создать новый React-компонент, который будет получать этот поток, "на лету" парсить из него частичный JSON и рендерить интерактивную панель, обновляющуюся в реальном времени.

---

#### 2. Задачи на Бэкенде (Backend Tasks - NestJS)

##### 2.1. Модифицировать `SupervisorSGRService` для стриминга сырых токенов
-   **Задача**: Изменить `async` генератор `executeSGRWorkflowWithStreaming`, чтобы он напрямую пробрасывал поток токенов от LLM.
-   **Реализация**:
    1.  В методе, вызывающем LLM (например, `executeReasoningStepWithStreaming`), нужно использовать опцию стриминга (`stream: true`).
    2.  Генератор `executeSGRWorkflowWithStreaming` должен перебирать чанки (chunks) из стрима LLM.
    3.  Каждый чанк (который является просто строкой, частью будущего JSON) нужно `yield`-ить дальше.
    4.  Тип события, которое `yield`-ится, должен быть четко определен, например: `{ type: 'SGR_TOKEN_CHUNK', payload: { token: '...' } }`.

##### 2.2. Адаптировать `BusinessSetupSubscriptionsResolver`
-   **Задача**: Убедиться, что GraphQL-подписка может обрабатывать и отправлять клиенту этот новый поток мелких событий `SGR_TOKEN_CHUNK`.
-   **Реализация**: Вероятно, здесь не потребуется больших изменений. `PubSub` и GraphQL Subscriptions хорошо справляются с потоковой передачей множества быстрых событий. Главное — чтобы резолвер был подписан на правильное событие и корректно передавал `payload` клиенту.

---

#### 3. Задачи на Фронтенде (Frontend Tasks - React)

Это самая объемная часть, так как здесь создается весь пользовательский опыт.

##### 3.1. Создать `useSgrStreamingParser` React-хук
-   **Задача**: Создать хук, который будет инкапсулировать всю логику получения потока и его парсинга "на лету", подобно `AsyncSchemaParser` из Python-скрипта.
-   **Реализация**:
    1.  Внутри хук использует `useSubscription` от Apollo Client для подписки на `SGR_TOKEN_CHUNK`.
    2.  Он будет иметь внутреннее состояние: `const [rawJson, setRawJson] = useState('')` и `const [parsedState, setParsedState] = useState({})`.
    3.  При получении каждого нового токена он добавляет его к `rawJson`.
    4.  **Ключевая логика**: После каждого обновления `rawJson` хук запускает функцию-парсер. Эта функция, используя **регулярные выражения**, будет пытаться извлечь из неполной JSON-строки известные поля (`reasoning_steps`, `current_situation`, `function.tool`, `function.query` и т.д.).
    5.  Извлеченные данные помещаются в `parsedState`.
    6.  Хук возвращает `parsedState`, который теперь можно использовать для рендеринга.

##### 3.2. Создать компонент-визуализатор `SgrVisualizationDashboard.tsx`
-   **Задача**: Сверстать React-компонент, который будет аналогом `rich`-дашборда.
-   **Реализация**:
    1.  Компонент получает `parsedState` от хука `useSgrStreamingParser`.
    2.  Он состоит из дочерних компонентов для каждого блока:
        -   `PipelineView.tsx`: Отображает все возможные шаги (`generate_plan`, `web_search`...) и подсвечивает текущий, основываясь на `parsedState.function.tool`.
        -   `CurrentThoughtView.tsx`: Рендерит `parsedState.reasoning_steps` и `parsedState.current_situation`. Текст в этих блоках будет появляться "в прямом эфире".
        -   `ToolCallView.tsx`: Показывает, какой инструмент (`tool`) и с какими параметрами (`query`, `title` и т.д.) AI сейчас "собирает".
    3.  **Анимации**: Использовать `framer-motion` для плавного появления блоков и текста, чтобы создать ощущение "живой" системы.

##### 3.3. Интегрировать в существующий чат
-   **Задача**: Встроить дашборд в интерфейс чата.
-   **Реализация**:
    1.  Когда бэкенд начинает "думать", в чате появляется не просто "AI is thinking...", а компонент `SgrVisualizationDashboard`.
    2.  Он обновляется на месте, пока идет стриминг.
    3.  Когда стриминг завершен и AI выполнил действие, дашборд можно "схлопнуть" в компактное сообщение-сводку о выполненном действии.
